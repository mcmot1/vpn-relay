# Экспериментальный AmneziaWG с входным узлом

Исходники VPN-сервера находятся в `amneziawg-fork/`. База форка — [AmneziaWG `v3.1.20261116`](https://github.com/amnezia-vpn/amneziawg-go/tree/v3.1.20261116), коммит `08fe3d33bbb116be09a6183d02609311b8b0c9e8`. Входной узел пересылает датаграммы через GOST Relay в WSS. Для сравнения доступны штатная и три экспериментальные сборки VPN-сервера с одной и той же базой.

## Установка из GitHub на Ubuntu 24.04

Выполните на каждом VPS в Bash от обычного пользователя с доступом к `sudo`. [Выпуск `v0.5.0`](https://github.com/mcmot1/vpn-relay/releases/tag/v0.5.0) содержит готовые сборки для `amd64` и `arm64`. Архивы публичные. Для установки не нужны GitHub CLI, учётная запись или Go.

```bash
sudo apt-get update && sudo apt-get install -y ca-certificates curl openssl python3
release=v0.5.0
case $(uname -m) in
    x86_64) arch=amd64 ;;
    aarch64|arm64) arch=arm64 ;;
    *) printf '%s\n' 'Поддерживаются только amd64 и arm64.' >&2; exit 1 ;;
esac
archive=vpn-relay-linux-$arch.tar.gz
base="https://github.com/mcmot1/vpn-relay/releases/download/$release"
download_dir=$(mktemp -d "$HOME/vpn-relay-$release.XXXXXX") && cd "$download_dir" &&
    curl -fsSLO "$base/$archive" && curl -fsSLO "$base/SHA256SUMS" &&
    sha256sum --ignore-missing --check SHA256SUMS &&
    tar -xzf "$archive" && cd "vpn-relay-linux-$arch"
```

После распаковки выполните на входном VPS:

```bash
bash install.sh ingress
```

На удалённом VPS установите релей и экспериментальную сборку AmneziaWG `adaptive`:

```bash
bash install.sh egress && bash install.sh vpn adaptive
```

Если релей уже настроен, выполните на удалённом VPS только `bash install.sh vpn adaptive`. Для контрольных измерений доступны `bash install.sh vpn baseline`, `bash install.sh vpn experimental` и `bash install.sh vpn smooth`. Установщик релея скачивает GOST с GitHub и сверяет SHA-256 до установки.

Тот же установщик работает из копии исходников, полученной через `git clone https://github.com/mcmot1/vpn-relay.git`. В этом режиме для `bash install.sh vpn` требуется Go 1.25 или новее. Для подготовки обоих архивов из исходников используется `bash scripts/package-release.sh`.

После установки настройте [удалённый VPS](#удалённый-vps) и [входной VPS](#входной-vps) через `sudo vpn-relay-configure`. На входном VPS параметр `--remote-host` задаёт доменное имя удалённого сервера. Команда `vpn` устанавливает бинарник в `/usr/local/bin/`. Его нужно выбрать в существующей userspace-службе AmneziaWG и применить конфигурацию интерфейса.

## Обновление

Обновление запускает администратор. Выберите опубликованный тег, подставьте его в `release` в блоке скачивания выше и повторите скачивание и проверку SHA-256 на обоих VPS. Из нового архива выполните `bash install.sh ingress` на входном VPS и `bash install.sh egress && bash install.sh vpn adaptive` на удалённом. Если используете другую сборку AmneziaWG, укажите её вместо `adaptive`.

Установщик обновляет исполняемые файлы, шаблоны и unit-файлы. Рабочий `/etc/vpn-relay/config.yaml`, TLS-материалы, параметры выпуска клиентов, клиентские `.conf` и конфигурация AmneziaWG сохраняются. Перезапустите `sudo systemctl restart vpn-relay.service` на каждом VPS. На удалённом VPS перезапустите также userspace-службу AmneziaWG, например `sudo systemctl restart awg-quick@awg0.service`, чтобы она загрузила новый бинарник. Действующие соединения могут кратковременно прерваться. Для отката повторите установку нужных компонентов из предыдущего проверенного выпуска и перезапустите службы.

## Эксперимент с длинами датаграмм

Сборка `adaptive` (`awg_adaptive`) распределяет дополнительный паддинг по трафику каждого узла. Каждые 12 исходящих байт UDP-полезной нагрузки с данными дают бюджет на один дополнительный байт. Кратковременный запас ограничен 256 байтами, поэтому суммарная экспериментальная добавка с момента создания peer составляет максимум 8,33%. Для исходных датаграмм длиннее 512 байт добавка составляет максимум 16 байт. Меньшие датаграммы могут использовать до 160 байт. Во всех случаях добавка учитывает доступный запас по размеру и потолок UDP-полезной нагрузки в 1200 байт.

После установки выберите `/usr/local/bin/amneziawg-go-adaptive` в userspace-службе на удалённом VPS и перезапустите её. Подключайтесь с тем же клиентским профилем. При установке только на сервере эксперимент меняет исходящий поток от сервера к клиенту.

Сборка `smooth` (`awg_smooth`) сохраняет штатный паддинг AmneziaWG и равновероятно добавляет от 0 до 160 байт к датаграмме с данными. Дополнительный диапазон сужается до половины оставшегося запаса по мере приближения к лимиту. Верхняя граница для добавки учитывает лимиты исходного форка и экспериментальный потолок UDP-полезной нагрузки в 1200 байт. Если датаграмма уже достигла потолка или превышает его, профиль оставляет её без дополнительного паддинга. Потолок относится только к экспериментальной добавке. Для маршрута с меньшим MTU настройте MTU VPN отдельно.

Синтетический замер на одинаковом наборе исходных длин запускается из `amneziawg-fork` командой `go test ./device -run '^TestPaddingProfilesOnFixedLengths$' -count=1 -v`. Он показывает число наблюдавшихся длин, долю датаграмм в полосах сеточного профиля, накладные расходы и вероятность совпадения длины у пары пакетов. Для оценки распознаваемости сетевым фильтром требуются замеры на реальном маршруте.

Сборка с тегом `awg_experimental` добавляет паддинг к исходящим пакетам с IP-данными после штатной обработки длины и до шифрования. Если в текущий предел размера помещается весь диапазон, длина UDP-датаграммы округляется вверх до границы в 128 байт и увеличивается ещё на случайные 0–31 байт. При расчёте предела учитываются UDP-окно узла, MTU туннеля с накладными расходами AWG и размер буфера. Рукопожатия и keepalive идут штатным путём.

Паддинг находится внутри аутентифицированной полезной нагрузки AWG. Приёмник уже обрезает её до длины из заголовка IPv4 или IPv6. Поэтому серверную сборку можно проверить с обычным AmneziaWG 3.1 при совпадающих параметрах профиля. В такой конфигурации эксперимент меняет пакеты с данными в направлении от VPN-сервера к клиенту. Для эксперимента в обоих направлениях трафика нужен экспериментальный бинарник и на клиентской стороне.

Цель эксперимента — измерить, как объединение соседних длин влияет на распознаваемость и сколько стоит по трафику. Группы длин сами могут стать заметным статистическим признаком. Для сравнения оставьте тот же WSS-релей, AWG-профиль, MTU и нагрузку. Смените только бинарник на удалённом VPS. Сравните распределения длин по направлениям, объём переданных данных, задержку и долю успешных соединений. Для длин AWG снимайте измерения на UDP-участке, поскольку на межсерверном участке снаружи видны TCP и TLS.

### Сборка и запуск эксперимента

Из корня проекта в Linux с Go 1.25 или новее:

```sh
cd amneziawg-fork
go test ./...
go test -tags awg_experimental ./...
go test -tags awg_smooth ./...
go test -tags awg_adaptive ./...
go build -trimpath -o ../dist/amneziawg-go-baseline .
go build -trimpath -tags awg_experimental -o ../dist/amneziawg-go-experimental .
go build -trimpath -tags awg_smooth -o ../dist/amneziawg-go-smooth .
go build -trimpath -tags awg_adaptive -o ../dist/amneziawg-go-adaptive .
```

Используйте выбранный бинарник в userspace-службе AmneziaWG на удалённом VPS. Она должна запускать выбранный файл вместо штатного `amneziawg-go` и применять существующую конфигурацию интерфейса. При установке через kernel-модуль потребуется отдельный userspace-интерфейс для эксперимента. Для отката запустите userspace-службу с `amneziawg-go-baseline`. Путь от клиента и настройки релея для обеих сборок одинаковы.

## Схема развёртывания

```text
Клиент AmneziaWG ── UDP/51820 ──> входной VPS
                                 │
                                 └── GOST Relay в WSS, TCP/443 ──> удалённый VPS
                                                                     │
                                                 127.0.0.1:51821/UDP ┘
                                                        │
                                                        └── AmneziaWG ──> Интернет
```

На удалённом VPS уже должен работать AmneziaWG. Входной VPS передаёт исходные датаграммы AWG и возвращает ответы клиенту через тот же канал. Клиентские ключи и ключ VPN-сервера для работы релея не требуются. Для полных туннелей публичным адресом выхода остаётся адрес удалённого VPS.

На межсерверном участке заголовки и содержимое AWG находятся внутри TLS. Входной VPS проверяет сертификат удалённого VPS через `dialer.tls.secure: true`, а удалённый релей проверяет общий секрет. При подключении по IP укажите IP из поля SAN сертификата и задайте `dialer.tls.caFile` для самоподписанного сертификата. Сам туннель AWG зашифрован от клиента до VPN-сервера. При потере пакетов между VPS повторная передача TCP может увеличить задержку.

## Подготовка

1. Направьте A-запись домена межсерверного транспорта на удалённый VPS и получите TLS-сертификат для этого домена. У конфигураций IPv4-прослушивание. Для домена с AAAA-записью потребуется также настроить IPv6-прослушивание и firewall либо убрать AAAA.
2. Один раз создайте общий секрет командой `openssl rand -hex 32`. Введите этот же секрет в конфигураторе на обоих VPS. Конфигуратор запрашивает секрет отдельно и сохраняет его в закрытом файле `/etc/vpn-relay/config.yaml`.

## Удалённый VPS

1. Проверьте, что VPN принимает датаграммы на `127.0.0.1:51821/udp` с сетевого пространства хоста. Для AmneziaWG на хосте используйте соответствующий `ListenPort`. Если он в Docker, опубликуйте UDP-порт только на loopback хоста. Например, для внутреннего порта `51820/udp` укажите `127.0.0.1:51821:51820/udp`. Если локальный порт другой, укажите его через `--awg-port` в командах настройки обоих VPS.
2. В firewall VPS и правилах провайдера разрешите доступ к `443/tcp` с исходящего IP входного VPS. Ограничьте прямой внешний доступ к UDP-порту AWG, учитывая действующих клиентов. При Docker проверьте фактическую публикацию портов и правила провайдера. Маршрутизация и NAT для VPN-клиентов выполняются на удалённом VPS.
3. После `bash install.sh egress` создайте конфигурацию, указав реальные пути к сертификату и ключу. Введите общий секрет, когда программа его запросит.

   ```sh
   sudo vpn-relay-configure egress --fullchain /path/to/fullchain.pem --privkey /path/to/privkey.pem
   sudo systemctl enable vpn-relay.service && sudo systemctl restart vpn-relay.service
   ```

   При продлении сертификата обновите `/etc/vpn-relay/tls/fullchain.pem` и `/etc/vpn-relay/tls/privkey.pem`, затем перезапустите `vpn-relay.service`. Порт WSS по умолчанию `443/tcp`. Другой порт задайте через `--wss-port` на обоих VPS и в firewall.

## Входной VPS

Разрешите входящий `51820/udp` для клиентских сетей и исходящий `443/tcp` до удалённого VPS. После `bash install.sh ingress` подставьте **домен удалённого VPS из TLS-сертификата** и введите тот же общий секрет:

```sh
sudo vpn-relay-configure ingress --remote-host exit.example.net
sudo systemctl enable vpn-relay.service && sudo systemctl restart vpn-relay.service
```

На входном VPS адрес удалённого сервера хранится в `/etc/vpn-relay/config.yaml`, в разделе `chains → to-egress → egress-hop → egress → addr`. Имя из TLS-сертификата записывается туда же в `dialer.tls.serverName`. Посмотреть адрес и порт без вывода секрета можно командой `sudo grep -A1 -- '- name: egress$' /etc/vpn-relay/config.yaml`. Для частного CA укажите `dialer.tls.caFile` на читаемый службой PEM и сохраните `secure: true`.

При перезаписи конфигуратор сохраняет предыдущий YAML в `/etc/vpn-relay/config.yaml.previous`. После правок перезапустите `vpn-relay.service`. Просмотр ошибок на обоих VPS — `sudo journalctl -u vpn-relay.service -n 50 --no-pager`.

## Клиент и проверка

На **удалённом VPS** с запущенным интерфейсом AmneziaWG и утилитой `awg` 3.1 сохраните настройки выпуска один раз. Подставьте имя интерфейса, его постоянный файл `awg-quick` и **адрес входного VPS**:

```bash
sudo vpn-relay-configure client-init \
  --interface awg0 \
  --server-config /etc/amnezia/amneziawg/awg0.conf \
  --endpoint entry.example.net:51820 \
  --dns 1.1.1.1
```

По умолчанию пул берётся из IPv4-подсети в поле `Address` сервера. При необходимости задайте пул явно через `--pool`, а исходящие маршруты через `--allowed-ips`. Для каждого нового клиента передавайте только имя файла:

```bash
sudo vpn-relay-configure client phone
```

Команда выпустит `/etc/vpn-relay/clients/phone.conf` с правами `0600` и автоматически выберет свободный адрес с учётом работающих и записанных peers. Для каждого устройства используйте отдельное имя. Для передачи через SSH обычному пользователю скопируйте профиль в его домашний каталог с правами `0600`:

```bash
sudo install -o "$(id -u)" -g "$(id -g)" -m 0600 /etc/vpn-relay/clients/phone.conf "$HOME/phone.conf"
```

Чтобы задать адрес и путь вручную, используйте полный вариант команды:

```bash
sudo vpn-relay-configure client \
  --interface awg0 \
  --server-config /etc/amnezia/amneziawg/awg0.conf \
  --address 10.8.0.2/32 \
  --endpoint entry.example.net:51820 \
  --output /root/phone.conf
```

Команда выдаёт новые ключи, сохраняет peer в настройках интерфейса и добавляет его в работающий AmneziaWG. Клиентский файл имеет права `0600`. По умолчанию через VPN направляется IPv4-трафик. Для других маршрутов задайте `--allowed-ips`, а для явного DNS — `--dns`. Передайте `.conf` на клиентское устройство и импортируйте его в AmneziaWG 3.1.

1. Для существующего клиента достаточно поменять `Endpoint` в копии его профиля на адрес входного VPS с портом `51820`.
2. Подключитесь и проверьте свежее рукопожатие в клиенте и на удалённом VPS через `awg show` в том же сетевом пространстве, где работает VPN. Затем передайте данные в туннеле. Если профиль направляет интернет-трафик в туннель, внешний адрес клиента должен совпасть с адресом выхода удалённого VPS.
3. Проверьте два клиента одновременно и повторите подключение после паузы, перезапуска релея и смены сети на клиенте. Проверьте извне, что прямой вход на AWG-порт удалённого VPS закрыт, а `443/tcp` доступен с входного VPS.

Для диагностики проверяйте последовательно публичный UDP-порт на входе, TLS до удалённого узла и локальный UDP-порт AmneziaWG. При пакетных потерях отдельно сравните скорость и задержку с прямым подключением. Успешное рукопожатие подтверждает связность, а устойчивость к DPI оценивается на целевых сетях отдельно.
